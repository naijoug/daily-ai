## AI 热点
1. **Microsoft: state hackers automate attacks with the open-source AI pentest framework ARTEX, and the ConnectWise supply-chain incident was theirs too**: Microsoft's security blog says Storm-0940, a group tied to Chinese state interests, has used ARTEX since September (an open-source agentic AI pentest framework on GitHub that chains multiple LLM agents from recon to data theft with almost no human work) against hundreds of organizations worldwide; in several cases it took under 3 hours from picking a target to privileged cloud access. It abused already-authorized credentials of the ConnectWise backup and management app to sign into Microsoft 365 tenants without user interaction, bypassing MFA; once in, it ran recon through Microsoft Graph, added credentials to other apps and tried to escalate (the rohanpaul summary mentions one app granting itself Global Admin). Most attempts still failed, e.g. a 150,000+ password-spray all failed, and a successful sign-in doesn't mean data was stolen. Teams using ConnectWise or who've granted third-party apps M365 access should check service-principal sign-ins, app credentials and permission changes since October 15, as Microsoft advises. https://www.microsoft.com/en-us/security/blog/2026/10/21/storm-0940-uses-artex-agentic-ai-connectwise-supply-chain-compromise/ ｜ https://x.com/rohanpaul_ai/status/2113113477552169349 ｜ https://thehackernews.com/2026/10/china-linked-hackers-use-artex-ai.html

5. **Nathan Lambert's Harvard talk: where open models stand**: He says open models trail the closed frontier by about 3–5 months and the gap is shrinking; Chinese open models lead on performance, downloads and paper citations, while US open models trail Chinese ones by 3–4 months. He thinks "distillation" is overrated: public research shows no huge gains from SFT on reasoning traces, and RL compute now exceeds pretraining. America's lasting edge is compute, with the top five US labs having on average 16x the compute of China's top five. He also argues banning open source won't stop bad actors and only hurts the economy, and suggests national risk standards that assess "marginal risk" per model. Full slides are public. https://natolambert.com/slides/2026/harvard/lecture.html ｜ https://x.com/shao__meng/status/2113092271503818988
> [zh] **Nathan Lambert 哈佛讲座：开源模型的现状**：他认为开源模型落后闭源前沿约 3–5 个月，差距还在缩小；性能、下载量、论文引用三项中国开源模型都领先，美国开源模型又比中国落后 3–4 个月。他认为「蒸馏」被高估了：公开研究里看不到用推理过程做 SFT 有巨大提升，现在强化学习的算力也已经超过预训练。美国真正持久的优势是算力，前五家实验室的总算力平均是中国前五家的 16 倍。他还认为禁止开源挡不住坏人，只会伤害经济，建议由国家统一风险标准，按模型评估「额外风险」。讲义全文公开。

## 有趣用法和干货
1. **Cloudflare cuts AI code review cost per run from $2.43 to $0.77 (-68%)**: Median review time falls from 4m09s to 1m32s, and the share of code-quality findings adopted by authors rises from 34% to 59%. On the bill, cache writes are 43%, cache reads 34% and output only 23%, so money mostly goes to repeated context. About 40% of the savings come from engineering: splitting the 11k–21k-token tool definitions and system prompt shared across repos into a separate cached prefix (previously bundled with working directory and date, giving only 14%–26% cache hit on the first request); the three review roles share one prefix, one writes the cache and the others wait to read it; removing tools sub-agents don't use; reading files in parallel; skipping roles with nothing new on re-review; and not running an extra summary round after the verdict. The other ~60% comes from model choice and reasoning effort: the coordinator uses Opus 5.5 medium, and Sonnet 5.5 has the same unit price as Sonnet 5 but far fewer tokens, 47%–62% cheaper. The code-quality role at high effort costs only about 2 cents more and finds 58% more severe and warning-level issues; performance and security roles at medium did miss issues, so high is next. Teams running their own agents can audit item by item. https://blog.cloudflare.com/obsessive-inference-optimization ｜ https://x.com/shao__meng/status/2113098764324159608
> [zh] **Cloudflare 把 AI 代码审查单次成本从 2.43 美元降到 0.77 美元（-68%）**：审查耗时中位数从 4 分 9 秒降到 1 分 32 秒，代码质量类发现被作者采纳的比例反而从 34% 升到 59%。账单里缓存写入占 43%、缓存读取占 34%，输出只占 23%，所以钱主要花在重复的上下文上。省下的钱约 4 成来自工程改动：把各仓库共用的 11k–21k token 工具定义和系统提示拆成独立的缓存前缀（原来跟工作目录、日期拼成一个块，首个请求的缓存命中率只有 14%–26%）；三个审查角色共用同一前缀，一个写缓存，其余等它写完再读；去掉子 agent 用不上的工具；改成并行读文件；复审时跳过没有新内容的角色；结论发出后不再多跑一轮写总结。其余约 6 成来自换模型和调推理强度：协调角色用 Opus 5.5 medium，Sonnet 5.5 单价和 Sonnet 5 一样，但 token 用量少得多，成本低 47%–62%。代码质量角色用 high effort 只贵约 2 美分，严重和警告级发现多 58%；性能、安全角色在 medium 下确实漏掉了问题，下一步测 high。自己跑 agent 的团队可以照着逐项排查。
2. **AgentReady: an open spec for making websites usable by AI agents; only two things really make agents fail**: Released by ora with Vercel, Stripe, Auth0, Mintlify, Tavily and others (MIT license). In a controlled experiment serving the same docs site in 19 configurations, only "the answer appears only after JS rendering" and "403 returned to agents" caused answers to be missed; llms.txt, JSON-LD, sitemaps and Markdown mirrors changed nothing. Agents mostly find llms.txt and openapi.json through links on the page and don't guess paths; when the official site is unreadable they answer from third-party pages, and the odds of an answer missing the facts the user asked about are 3.7x normal. The spec has MUST/SHOULD/MAY across three steps, find, read, act: MUST includes robots allowing agents, answers in the initial HTML, real HTTP status codes, and at least an MCP server or CLI. https://ora.ai/blog/agentready-launch ｜ https://x.com/shao__meng/status/2113084778673287480
> [zh] **AgentReady：让网站能被 AI agent 用的开放规范，只有两件事真会让 agent 失败**：ora 联合 Vercel、Stripe、Auth0、Mintlify、Tavily 等发布（MIT 许可）。受控实验里，同一个文档站用 19 种配置提供，只有「答案只在 JS 渲染后才出现」和「对 agent 返回 403」会导致拿不到答案；llms.txt、JSON-LD、sitemap、Markdown 镜像都不改变结果。agent 主要靠页面上的链接找到 llms.txt 和 openapi.json，不会去猜路径；读不到官网时，它转而用第三方页面作答，回答里完全没有用户要问的事实的概率是正常情况的 3.7 倍。规范按「找到、读取、操作」三步分出 MUST/SHOULD/MAY：MUST 包括 robots 放行 agent、答案出现在初始 HTML 里、返回真实的 HTTP 状态码、至少提供 MCP 服务器或 CLI 之一。
3. **Stanford CS 329Z lecture 9: how to choose an optimization method for agent systems**: Assumes you have data, a system and evaluation metrics. Start with cheap, sample-efficient context optimization (few-shot selection and ordering, DSPy/MIPROv2, TextGrad, GEPA); when that isn't enough, you want to distill capability into a smaller model, or prompts keep growing, change the weights (SFT on teacher trajectories, GRPO reinforcement learning, on-policy distillation); agents can also optimize themselves (Darwin Gödel Machine, Meta-Harness, karpathy's autoresearch), but then the evaluation metric itself most needs control to prevent gaming. BetterTogether finds that sometimes the best order is prompt tuning, then weight tuning, then prompt tuning again. Lecture PDF available for download. https://web.stanford.edu/class/cs329z/slides/lecture09.pdf ｜ https://x.com/shao__meng/status/2113105750818164882
> [zh] **Stanford CS 329Z 第 9 讲：agent 系统优化方法怎么选**：前提是数据、系统、评估指标三样都有。先做便宜、省样本的上下文优化（少样本示例挑选与排序、DSPy/MIPROv2、TextGrad、GEPA）；上下文优化不够、想把能力蒸馏到小模型、或 prompt 越写越长时，再改权重（教师模型的轨迹做 SFT、GRPO 强化学习、on-policy 蒸馏）；也可以让 agent 自己做优化（Darwin Gödel Machine、Meta-Harness、karpathy 的 autoresearch），但这时最需要把控的是评估指标本身，防止它钻空子。BetterTogether 的结论是，有时最好的顺序是先调 prompt、再调权重、最后再调一次 prompt。讲义 PDF 可直接下载。
