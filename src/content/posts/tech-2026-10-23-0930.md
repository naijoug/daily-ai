## 新产品
1. **MiniMax M3.1 Flash：开源权重，428B 总参数、23B 激活**：MiniMax 今天开源 M3.1 Flash，相比 M3 全面提升。推理效率上做了三件事：前三个全注意力层也换成稀疏注意力，全模型都是稀疏注意力；量化感知训练把路由 MoE 专家迁到 W4A4（共享专家除外），KV 从 Q8KV8 降到 Q8KV4；再按算卡功耗精细调度，让算力保持在高位。官方说它 10/19 上线后 72 小时处理了超过 100 万亿 token；首日就有昇腾、平头哥、昆仑芯、英伟达、AMD 等芯片，以及 Together、Fireworks、Modal 等云平台接入，vLLM、SGLang 也同步支持。想找一个能自己部署的强开源 agent/编码模型，可以把它列进候选。[魔搭](https://modelscope.cn/models/MiniMax/MiniMax-M3.1-Flash) ｜ [Hugging Face](https://huggingface.co/MiniMaxAI/MiniMax-M3.1-Flash) ｜ [IT之家](https://www.ithome.com/1/016/800.htm)
> [en] **MiniMax M3.1 Flash: open weights, 428B total / 23B active parameters**: MiniMax open-sources M3.1 Flash today, improved across the board over M3. Three things for inference efficiency: the first three full-attention layers are also switched to sparse attention, so the whole model is sparse attention; quantization-aware training moves the routed MoE experts to W4A4 (shared experts excepted) and drops KV from Q8KV8 to Q8KV4; and compute is scheduled finely against accelerator-card power draw to keep utilization high. The company says it processed over 100 trillion tokens in the 72 hours after its 10/19 launch; on day one chips from Ascend, T-Head, Kunlunxin, Nvidia and AMD and clouds such as Together, Fireworks and Modal were connected, with vLLM and SGLang supporting it in sync. Put it on your shortlist if you want a strong self-deployable open agent/coding model.
2. **EmbeddingGemma 2: Google open-sources a 740M multimodal embedding model**: it maps text (including code), images, video and audio into one 768-dimensional vector space, built from a 270M text backbone plus optionally loaded vision (170M) and audio (300M) encoders, so the other two can stay unloaded for text-only use. It supports 100+ languages, improves on code tasks by about 14% over the previous generation, has 8K context, vectors can be truncated to 128/256/512 dimensions (up to 6x storage savings), and instruction prefixes distinguish tasks such as retrieval, classification and clustering. Apache 2.0, aimed at running locally on phones and laptops, a good fit for on-device RAG or multimodal search. [Gemma 文档](https://ai.google.dev/gemma/docs/embeddinggemma) ｜ [Google 博客](https://blog.google/innovation-and-ai/technology/developers-tools/embeddinggemma-2) ｜ [Hugging Face](https://huggingface.co/google/embeddinggemma-2)
> [zh] **EmbeddingGemma 2：Google 开源 740M 多模态嵌入模型**：把文本（含代码）、图片、视频、音频映射到同一个 768 维向量空间，由 270M 文本主干加可按需加载的视觉（170M）、音频（300M）编码器组成，只用文本时可以不加载另外两块。支持 100 多种语言，代码任务比上一代提升约 14%，上下文 8K，向量可截断到 128/256/512 维（存储最多省 6 倍），用指令前缀区分检索、分类、聚类等任务。Apache 2.0 协议，面向手机和笔记本本地跑，做端侧 RAG 或多模态搜索很合适。
3. **Loom Record for agents: record your screen and hand it straight to an AI**: Loom's new Mac app adds "record for agents", capturing video, voice and on-screen actions together and automatically turning them into a prompt any AI tool can execute, so you don't have to type out what happened on screen; it also works in the Chrome extension, free. The new Mac app also supports precise region recording, 4K by default. Launched on Product Hunt today. Handy for reproducing bugs for an agent or demoing a workflow. [Loom](https://www.loom.com/) ｜ [Product Hunt](https://www.producthunt.com/products/loom)
> [zh] **Loom Record for agents：录一段屏幕，直接交给 AI 去做**：Loom 新版 Mac 应用加了「为 agent 录制」，同时录下视频、声音和屏幕上的操作，自动转成任何 AI 工具都能执行的 prompt，省得你打字描述屏幕上发生了什么；Chrome 扩展也能用，免费。新版 Mac 应用还支持精确区域录制，默认 4K。今天在 Product Hunt 上线。给 agent 复现 bug、演示一段操作流程时会很顺手。
4. **Hy-Memory-30B-A3B: Tencent Hunyuan's small model dedicated to "writing memory"**: about 3B active parameters, responsible only for the write step in an external memory framework, i.e. deciding what to remember, how detailed, and how to update the store when new information arrives; a drop-in replacement for the general-purpose large model in Mem0, MemOS and Hy-Memory. Training has two steps: on-policy distillation first, then reinforcement learning scored per memory chunk; in evaluation only the write model is swapped while retrieval, answer models and the judge stay fixed, and it transfers to EverMemOS, unseen in training. Apache 2.0. Worth trying if you build long-term memory for agents and find calling a large model on every write too expensive. [Hugging Face](https://huggingface.co/tencent/Hy-Memory-30B-A3B)
> [zh] **Hy-Memory-30B-A3B：腾讯混元专门「写记忆」的小模型**：约 3B 激活参数，只负责外部记忆框架里的写入环节，也就是决定记什么、记多细、新信息来了怎么更新记忆库，可以直接替换 Mem0、MemOS 和 Hy-Memory 里原本的通用大模型。训练分两步：先做 on-policy 蒸馏，再用按记忆块打分的强化学习；评测时只换写入模型，检索、回答模型和裁判都固定，在训练时没见过的 EverMemOS 上也能迁移。Apache 2.0。给 agent 做长期记忆、又嫌每次写入都调大模型太贵的，可以试试。
5. **MOSS-Image: Fudan OpenMOSS open-sources a text-to-image model with good Chinese typography**: comes in Base and SFT versions, Apache 2.0, loaded with a custom diffusers pipeline, with ComfyUI nodes too. Besides natural-language prompts it supports tag sequences and JSON layouts to control text position and object placement; the official example is three lines of handwritten Chinese on a fridge sticky note. Currently near the top of the Hugging Face trending list. [GitHub](https://github.com/OpenMOSS/MOSS-Image) ｜ [Hugging Face](https://huggingface.co/OpenMOSS-Team/MOSS-Image-SFT)
> [zh] **MOSS-Image：复旦 OpenMOSS 开源文生图模型，中文排字表现好**：分 Base 和 SFT 两个版本，Apache 2.0，用 diffusers 自定义 pipeline 加载，也提供 ComfyUI 节点。除了自然语言 prompt，还支持标签序列和 JSON 布局来控制文字位置和物体摆放，官方示例就是在冰箱便利贴上手写三行中文。目前在 Hugging Face 趋势榜靠前。

1. **GitHub 用 AI 把 Copilot 运行时从 TypeScript 整体迁到 Rust**：Copilot CLI、Copilot 应用和 SDK 背后的运行时用了约 14.5 周、128 个 PR 完成迁移，替换 80 多万行代码，绝大部分由 agent 生成，靠编译、测试和人工评审抓回归。做法是逐个组件替换，中间用临时的 N-API 互操作层衔接，迁移期间照常发了 135 个版本；4478 次 cargo check 里 87.1% 一次通过。结果是启动、建会话加一轮交互从 5.25 秒降到 292 毫秒，还省掉每个客户端约 100MB 的 V8 内存，可以通过 C ABI 直接嵌进宿主应用。评论区的关注点是取消、重试、背压这类行为光靠编译验证不了。想用 AI 做大规模重写的团队值得细读。[InfoQ 中文](https://www.infoq.cn/article/zGqDWHF8tHDtlYcImAJS) ｜ [InfoQ 英文原文](https://www.infoq.com/news/2026/10/github-copilot-rust-migration/)
> [en] **GitHub used AI to migrate the Copilot runtime from TypeScript to Rust wholesale**: the runtime behind Copilot CLI, the Copilot app and the SDK was migrated in about 14.5 weeks and 128 PRs, replacing 800,000+ lines of code, mostly generated by agents, with compilation, tests and human review catching regressions. They replaced component by component, bridged by a temporary N-API interop layer, and shipped 135 releases as usual during the migration; 87.1% of 4,478 cargo checks passed first try. Results: startup plus creating a session plus one interaction dropped from 5.25 seconds to 292 ms, each client saves about 100MB of V8 memory, and it can be embedded directly into host apps through the C ABI. Commenters point out that behaviors like cancellation, retries and backpressure can't be verified by compilation alone. Worth a close read for teams considering large AI-driven rewrites.

1. **V2EX：Codex 桌面版崩溃转储会悄悄吃掉几十上百 GB**：macOS 版 Codex 的崩溃上报卡住时，Crashpad 会不停往本地写转储文件且没有任何提示，官方 issue 6 月就开了至今未修，有人一天涨 4.9GB，评论里有人删了 80 多 GB。自查命令：`du -sh ~/Library/Application\ Support/Codex/Crashpad ~/Library/Application\ Support/com.openai.codex/web/Crashpad`；清理时先退出 Codex，再删掉其中 pending、completed、new、attachments 目录里的内容（保留 Crashpad 文件夹和 settings.dat）。其他 Electron 应用用的是同一套机制，也可以顺便查。[V2EX](https://www.v2ex.com/t/1250986) ｜ [GitHub issue](https://github.com/openai/codex/issues/25921)
> [en] **V2EX: Codex desktop crash dumps silently eat tens to hundreds of GB**: when crash reporting hangs in macOS Codex, Crashpad keeps writing dump files locally with no notice; the official issue was opened in June and is still unfixed, one user saw 4.9GB growth in a day, and a commenter deleted 80+ GB. Check command: `du -sh ~/Library/Application\ Support/Codex/Crashpad ~/Library/Application\ Support/com.openai.codex/web/Crashpad`; to clean up, quit Codex first, then delete the contents of the pending, completed, new and attachments directories (keep the Crashpad folder and settings.dat). Other Electron apps use the same mechanism, so check them too.
2. **LinuxDo：基于 Hindsight 的企业级记忆系统怎么分库**：楼主总结了一次架构讨论，结论是不要「一个 agent 一个记忆库」，而是记忆跟人走：每人一个个人库，编码场景按「用户 + 项目」再建一个库，团队库要人工审核后才发布。分工原则是用库做强隔离（用户、项目、权限），用标签做库内的范围过滤，用元数据记录来源（哪个产品、哪次会话、哪个 commit），并提醒后台的自动整合也必须守同样的边界，光靠召回时按标签过滤不够安全。给多 agent 产品设计记忆的可以参考。[LinuxDo](https://linux.do/t/topic/3061870)
> [en] **LinuxDo: how to split databases in an enterprise memory system built on Hindsight**: the poster summarizes an architecture discussion whose conclusion is not "one memory store per agent" but memory that follows people: a personal store per person, a further "user + project" store for coding scenarios, and team stores published only after manual review. The division of labor: use stores for hard isolation (users, projects, permissions), tags for scoping within a store, and metadata to record provenance (which product, which session, which commit), and background auto-consolidation must obey the same boundaries, since filtering by tag only at recall time isn't safe enough. A useful reference for designing memory for multi-agent products.
