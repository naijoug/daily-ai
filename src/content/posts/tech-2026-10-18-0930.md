## 新产品 / 开源
1. **Pele: a Mermaid renderer open-sourced by the Obsidian team**: renders Mermaid text directly to SVG, synchronously, with zero runtime dependencies; colors and fonts are controlled by CSS variables so switching themes needs no re-render; the site's comparison is 230 kB gzipped versus Mermaid.js's 1.6 MB, 0.05–0.3 ms per diagram versus 6–82 ms, and narrow screens re-lay out rather than scaling the whole thing. It supports all diagram types built into Mermaid 12.1.0, the parser is validated with Mermaid's own test cases and differential fuzzing, MIT-licensed, and `npm install pele` is all it takes. Worth a look if you embed flowcharts in doc sites, note apps or agent output. [Website](https://pele.run/) ｜ [GitHub](https://github.com/obsidianmd/pele) ｜ [HN discussion](https://news.ycombinator.com/item?id=50132193) (230 points: someone grumbles that Mermaid's real pain is poor layout of complex diagrams and styling is a minor issue; others think producing SVG without a browser environment makes it easy to embed in more places)
> [zh] **Pele：Obsidian 团队开源的 Mermaid 渲染器**：把 Mermaid 文本直接渲染成 SVG，同步执行、零运行时依赖，颜色和字体用 CSS 变量控制，切换主题不用重新渲染；官网的对比是 gzip 后 230 kB 对 Mermaid.js 的 1.6 MB，单图渲染 0.05–0.3 ms 对 6–82 ms，窄屏会重新排版而不是整体缩放。支持 Mermaid 12.1.0 内置的全部图表类型，解析器用 Mermaid 自己的测试用例和差分模糊测试验证过，MIT 许可，`npm install pele` 即可用。在文档站、笔记应用或 Agent 输出里嵌流程图的人可以看看。[官网](https://pele.run/) ｜ [GitHub](https://github.com/obsidianmd/pele) ｜ [HN 讨论](https://news.ycombinator.com/item?id=50132193)（230 分：有人吐槽 Mermaid 真正的痛点是复杂图的布局很差，样式反倒是小问题；也有人认为不依赖浏览器环境就能出 SVG，方便嵌到更多地方）
2. **tsc-ts (Vercel Labs)**: ports the Go TypeScript 7.0.2 compiler (tsgo) module by module back to TypeScript, then compiles it to a native executable with scriptc. The README lists the scanner, parser, type checker, JS and .d.ts output, `--build` incremental compilation and other parts, all matching tsgo item by item across TypeScript's roughly 12,500 test files, and it also provides the same API server as `tsc --api`. Currently an experimental project, Apache 2.0. [GitHub](https://github.com/vercel-labs/tsc-ts) ｜ [HN discussion](https://news.ycombinator.com/item?id=50132911) (someone measured it faster than the Go version but points out it is actually written in the TypeScript subset scriptc supports, with some subtle semantic differences; others don't see why port back something tsgo already makes native)
> [zh] **tsc-ts（Vercel Labs）**：把 TypeScript 7.0.2 的 Go 版编译器（tsgo）逐模块移植回 TypeScript，再用 scriptc 编译成原生可执行文件。README 列出扫描器、解析器、类型检查、JS 和 .d.ts 输出、`--build` 增量编译等各部分，都在 TypeScript 约 12,500 个测试文件上和 tsgo 逐项比对一致，还提供和 `tsc --api` 相同的 API 服务。目前是实验项目，Apache 2.0。[GitHub](https://github.com/vercel-labs/tsc-ts) ｜ [HN 讨论](https://news.ycombinator.com/item?id=50132911)（有人实测比 Go 版还快，但指出它其实是用 scriptc 支持的 TypeScript 子集写的，语义上还有些细微差异；也有人看不懂 tsgo 本来就是原生的，为什么还要再移植回来）
3. **esp32sim (Show HN)**: an open-source ESP32 emulator written in Rust, covering ESP32, S3 (Xtensa) and C3, C6 (RISC-V), booting real mask ROM and second-stage bootloader and running unmodified firmware, and also emulating a virtual Wi-Fi access point (WPA2, DHCP, NAT to the real network) and several displays. It can be compiled to WebAssembly to run in the browser; S3 is marked mature while C3 and C6 are still drafts, MIT-licensed. The author most wants to know how far embedded developers need it to go before they'd use it for development and CI. [GitHub](https://github.com/mikroverk/esp32sim) ｜ [Try online](https://mikroverk.github.io/esp32sim/) ｜ [HN discussion](https://news.ycombinator.com/item?id=50131189) (one says IoT teams could have mobile and backend integrate against real firmware before hardware arrives; another asks how it differs from Wokwi, and another finds the README too AI-sounding)
> [zh] **esp32sim（Show HN）**：用 Rust 写的开源 ESP32 模拟器，覆盖 ESP32、S3（Xtensa）和 C3、C6（RISC-V），启动真实的掩码 ROM 和二级引导程序，跑不经修改的固件，还模拟了虚拟 Wi‑Fi 热点（WPA2、DHCP，可以 NAT 到真实网络）和几种屏幕。可以编译成 WebAssembly 在浏览器里跑，S3 已标为成熟，C3、C6 还是草稿，MIT 许可。作者最想知道嵌入式开发者要它支持到什么程度才愿意拿来做开发和 CI。[GitHub](https://github.com/mikroverk/esp32sim) ｜ [在线试玩](https://mikroverk.github.io/esp32sim/) ｜ [HN 讨论](https://news.ycombinator.com/item?id=50131189)（有人说 IoT 团队可以让移动端和后端在拿到硬件前就对着真实固件联调；也有人问它和 Wokwi 有什么区别，还有人嫌 README 的 AI 味太重）
4. **gopls supports interactive refactoring**: the Go team and the Dart team jointly proposed a new LSP capability that lets a language server ask the user for parameters before changing code. So "add struct tags" can choose `json,yaml,db` and naming styles like snake_case, "implement interface" can search any interface name and generate method stubs, and moving declarations across files and packages (with helper declarations used only by it, cleaning up imports) is on the way. gopls v0.24.0 and VS Code Go extension v0.56.0 are available, with proofs of concept for Neovim and Emacs. This is the official Go blog from October 16, not covered before. [Go 博客](https://go.dev/blog/interactive-refactoring) ｜ [LSP 提案](https://github.com/microsoft/language-server-protocol/issues/1164)
> [zh] **gopls 支持交互式重构**：Go 团队和 Dart 团队一起向 LSP 提了一个新能力，让语言服务器在改代码前可以弹窗问用户参数。于是「添加结构体标签」可以选 `json,yaml,db` 和 snake_case 等命名风格，「实现接口」可以搜索任意接口名并自动生成方法桩，跨文件、跨包移动声明（连同只被它用到的辅助声明一起搬，并清理 import）也在路上。gopls v0.24.0 和 VS Code Go 扩展 v0.56.0 已可用，Neovim、Emacs 有概念验证。这是 10 月 16 日的 Go 官方博客，之前没写过。

1. **Codex desktop's Crashpad dumps can fill your disk**: this issue, filed in June, hit HN tonight. The latest comment says that on the current ChatGPT.app 26.1007, the two Crashpad directories total about 323 GB and 4 million+ files, leaving 1.4 GB of disk, with no warning in the app. Someone earlier analyzed the cause: `browser_crashpad_handler` crashes at startup when a Mach port call fails, and since it also monitors itself, it writes a dump of itself and restarts, about one per second, roughly 15 GB per day, and the `pending` directory has no size cap. Mac users can first look at `~/Library/Application Support/Codex/Crashpad/pending` and `com.openai.codex/web/Crashpad`; a comment gives a temporary workaround of clearing them and making the directory read-only. [GitHub issue](https://github.com/openai/codex/issues/25921) ｜ [HN discussion](https://news.ycombinator.com/item?id=50133231) (some are glad they kept these agents in Docker from the start; another says every git worktree duplicating build artifacts causes similar disk pressure; another reminds that the ChatGPT app settings have a storage page that shows usage)

5. **Google validates "magic state cultivation" on Willow, cutting error rates about 40x**: general-purpose, error-correctable quantum computing needs a large number of "magic states", estimated to take up to 95% of a quantum computer's resources. The cultivation method Google proposed in 2024 works like a filter; measured now on the Willow processor, errors are about 40x fewer than without cultivation, T-state logical fidelity reaches a record 99.99%, and it also demonstrated moving the state from a distance-3 color code into a distance-5 surface code, with the paper in Science. Google also says larger-scale validation is still needed. The blog is from October 15 and only showed up on Techmeme this period. [Google 博客](https://blog.google/innovation-and-ai/models-and-research/quantum-computing/magic-state-cultivation-quantum-computing/) ｜ [Techmeme](https://www.techmeme.com/261017/p19#a261017p19)
> [zh] **Google 在 Willow 上验证「魔术态培育」，错误率降约 40 倍**：要做通用、可纠错的量子计算，需要大量「魔术态」，有估计说它可能占掉整台量子计算机 95% 的资源。Google 2024 年提出的培育方法相当于一个过滤器，这次在 Willow 处理器上实测，错误比不培育时少了约 40 倍，T 态逻辑保真度达到创纪录的 99.99%，还演示了把状态从距离 3 的色码移植到距离 5 的表面码，论文发在 Science。Google 也说还需要更大规模的验证。博客是 10 月 15 日的，本时段才在 Techmeme 上出现。
