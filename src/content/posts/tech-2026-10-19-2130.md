## 新产品 / 开源
1. **Superlite: a "hand it off and walk away" plugin for Claude Code**: the author loves superpowers but dislikes that it stops for human approval 8–12 times per feature and runs only one implementation agent at a time. superlite asks one batch of questions and takes one approval, writes the plan as a task graph, and runs non-conflicting tasks in parallel: Opus only plans and dispatches (a hook forbids it from editing code), Sonnet writes most tasks, Haiku does small well-defined jobs, and finally a fresh Opus only picks out problems without changing anything; choices it would have asked you about are recorded as "rulings" so you know what to check first when you return. On the author's benchmark, a project scored by 177 hidden tests, the latest run passed everything in 16.1 minutes with up to 18 agents working at once, versus an average of 33.6 minutes over 3 runs for original superpowers. It never pushes or merges automatically. [Blog](https://contextfirst.blog/superlite-hand-an-agent-a-spec/) ｜ [GitHub](https://github.com/iha2/superlite) ｜ [HN discussion](https://news.ycombinator.com/item?id=50147492) (114 points. Several say superpowers was useful a few months ago but Opus 5.5 now writes the spec itself, assumes you agree and finishes the job, so such plugins are less necessary; others ask how many more tokens parallelism costs and whether multiple agents might edit each other's files)
> [zh] **Superlite：给 Claude Code 用的「交给它就走开」插件**：作者很喜欢 superpowers，但嫌它每个功能要停下来让人批准 8–12 次，还一次只跑一个实现 agent。superlite 改成只问一批问题、批准一次，把计划写成任务图，互不冲突的任务并行跑：Opus 只负责规划和派活（用 hook 禁止它改代码），Sonnet 写大部分任务，Haiku 做小而明确的活，最后由新开的 Opus 只挑问题、不动手；它原本会问你的选择都记成「裁决」，回来一看就知道先检查哪些。作者的基准是一个用 177 个隐藏测试打分的项目，最新一次 16.1 分钟全过，最多 18 个 agent 同时干活，superpowers 原版 3 次平均要 33.6 分钟。不会自动 push 或 merge。[博客](https://contextfirst.blog/superlite-hand-an-agent-a-spec/) ｜ [GitHub](https://github.com/iha2/superlite) ｜ [HN 讨论](https://news.ycombinator.com/item?id=50147492)（114 分。好几个人说 superpowers 几个月前有用，现在 Opus 5.5 自己就会写 spec、默认你同意然后直接做完，这类插件没那么必要了；也有人追问并行会多花多少 token、多个 agent 会不会改到彼此的文件）
2. **Mistral releases Timestral: the first family of time-series foundation models**: four sizes from 5M to 209M parameters, the largest ranking first on all three major public leaderboards (GIFT-Eval, TIME, fev-bench) with only two-thirds the parameters of the previous best. It does probabilistic and multivariate forecasting, supports covariates known only historically and future covariates known in advance, and runs on CPU; use it zero-shot or fine-tune it on your own data through Mistral Forge. Worth a try for capacity planning and monitoring-metric forecasting. [Mistral](https://mistral.ai/news/timestral/) ｜ [HN discussion](https://news.ycombinator.com/item?id=50150434) (some marvel that a forecasting model that took months five years ago now deploys in minutes; others doubt that time series and text are alike enough for "foundation models" to be very useful, and one complains the chart draws a 0.03 improvement as a 5x gap and asks how it compares with Nixtla TimeGPT)
> [zh] **Mistral 发布 Timestral：第一个时间序列基础模型系列**：有 4 个尺寸，从 5M 到 209M 参数，最大的那个在 GIFT-Eval、TIME、fev-bench 三个主要公开榜上都排第一，参数只有之前最好模型的三分之二。能做概率预测和多变量预测，支持只有历史值的协变量和提前已知的未来协变量，在 CPU 上也能跑；零样本直接用，也能通过 Mistral Forge 用自己的数据微调。做容量规划、监控指标预测的可以试试。[Mistral](https://mistral.ai/news/timestral/) ｜ [HN 讨论](https://news.ycombinator.com/item?id=50150434)（有人感慨五年前要花几个月做的预测模型现在几分钟就能上线；也有人质疑时间序列和文本本质不同，「基础模型」的实际用处有限，还有人吐槽图表把 0.03 的提升画成了 5 倍差距，问它和 Nixtla TimeGPT 比如何）
3. **A Qwen3-4B trained out of its AI voice (Show HN)**: the author first wrote an "AI voice" detector scoring weighted by em dashes, "not X but Y", triple parallelism, self-questioning and words like "delve"; human writing is usually under 15, original Qwen3-4B averages 121. Using distillation plus LoRA and a patch that changes only 4 neurons, three rounds got it to 12.5 while task completion stayed at 80% (one intermediate round scored lower but the model started refusing to take positions and inventing studies, so it was reverted). The article lays out the pitfalls of each round, which is more interesting than the result itself. The Q4_K_M quantization is 2.5 GB and runs directly in Ollama or llama.cpp. [Article](https://100toolkit.com/blog/deslop-model/) ｜ [Hugging Face](https://huggingface.co/erikkannike/qwen3-4b-deslop-v4) ｜ [HN 讨论](https://news.ycombinator.com/item?id=50151928)
> [zh] **把 AI 腔训掉的 Qwen3-4B（Show HN）**：作者先写了个「AI 腔」检测器，按破折号、「不是 X 而是 Y」、三连排比、自问自答、「delve」这类词加权计分，人类写作通常低于 15，原版 Qwen3-4B 平均 121。他用蒸馏加 LoRA，再配一个只改 4 个神经元的补丁，三轮下来做到 12.5 分，任务完成度保持在 80%（中间一轮分数更低，但模型开始不表态、编造研究，所以又改了回来）。文章把每轮踩的坑都写清楚了，比结果本身更有意思。Q4_K_M 量化版 2.5 GB，Ollama 或 llama.cpp 都能直接跑。
4. **STROT: use a large model only once at compile time, then classify and route locally (Show HN)**: you write an intent (e.g. "route tickets to the right workflow") and candidate actions; the large model is used only during the first compile to synthesize labeled data, input mapping and handling logic; afterwards every record is decided by a 144M local small model running on CPU, which the author says takes about 60 ms per record at no extra cost, outputting typed JSON with confidence and abstaining rather than guessing when unsure. MIT-licensed, `pip install strot-ai`. [GitHub](https://github.com/strot-ai/Project-STROT) ｜ [HN discussion](https://news.ycombinator.com/item?id=50148396) (some like the idea of "reason once, reuse the result forever"; others ask why not just have the large model write a program, and one says the README doesn't explain how it actually works)
> [zh] **STROT：只在编译时用一次大模型，之后在本地做分类和路由（Show HN）**：你写一句意图（比如「把工单分到正确的流程」）和候选动作，大模型只在第一次编译时用来合成标注数据、输入映射和处理逻辑；之后每条记录都交给一个 144M、跑在 CPU 上的本地小模型决策，作者说每条约 60 ms、没有额外费用，输出是带置信度的类型化 JSON，没把握时会弃权而不是乱猜。MIT 开源，`pip install strot-ai`。[GitHub](https://github.com/strot-ai/Project-STROT) ｜ [HN 讨论](https://news.ycombinator.com/item?id=50148396)（有人很认同「推理一次、之后一直复用结果」的思路；也有人反问，直接让大模型写个程序不就行了，还有人说 README 没讲清楚具体怎么做）
5. **headroom: compress content before it enters the model**: newly appeared on GitHub Trending today. It picks a compressor by content type locally, with separate ones for JSON, source code (AST-based) and plain text, and flags volatile content that would break the KV-cache prefix; the original is stored locally, and the model can call `headroom_retrieve` to get the full text back when needed. The README says it saves coding agents about 20% of tokens and JSON 60–95%. Use it as a library, local proxy or MCP server; `headroom wrap claude` wraps Claude Code directly. [GitHub](https://github.com/headroomlabs-ai/headroom)
> [zh] **headroom：在内容进模型之前先压缩**：今天 GitHub Trending 新冒出来的。它在本地按内容类型挑压缩器，JSON、源码（基于 AST）和普通文本各有一套，还会标出会破坏 KV 缓存前缀的易变内容；原文存在本地，模型需要时可以调 `headroom_retrieve` 取回全文。README 说能给 coding agent 省约 20% token，JSON 能省 60–95%。可以当库、本地代理或 MCP server 用，`headroom wrap claude` 就能直接包住 Claude Code。
6. **Harness Engineering 101: how to build an agent from scratch**: a 16-chapter open-source mini book. The core idea is that LLM APIs are stateless, so a "harness" is the program that builds, maintains and protects the message array, and the various agent designs are patches on that loop, each answering a specific problem that actually occurred. Each chapter is written as "what went wrong, the smallest patch, the cost of the patch", with a ~300-line pure-Python toy agent, from tool calling and why caching cares about ordering to context budgets. [GitHub](https://github.com/IsuruMaduranga/harness-engineering-101) ｜ [Read online](https://isuruwijesiri.com/harness-engineering-101/) ｜ [HN discussion](https://news.ycombinator.com/item?id=50151390) (the comments aren't very receptive: some dislike the anthropomorphic title, and one decided it was AI-written on reading the phrase "Load-Bearing")
> [zh] **Harness Engineering 101：从零讲怎么搭一个 agent**：16 章的开源小书。核心观点是 LLM API 没有状态，所谓 harness 就是负责构建、维护、保护那个消息数组的程序，agent 的各种设计都是给这个循环打的补丁，每个补丁都对应某个具体出过的问题。每章都按「出了什么问题、最小的补丁、补丁的代价」来写，配一个约 300 行的纯 Python 玩具 agent，从工具调用、缓存为什么要讲顺序，讲到上下文预算。[GitHub](https://github.com/IsuruMaduranga/harness-engineering-101) ｜ [在线阅读](https://isuruwijesiri.com/harness-engineering-101/) ｜ [HN 讨论](https://news.ycombinator.com/item?id=50151390)（评论区不太买账，有人嫌标题拟人化，有人读到「Load-Bearing」这个词就判定是 AI 写的）

4. **Left alone on a virtual desert island, Claude started to "play"**: MIT CSAIL researchers put several copies of Claude Opus 4.7 (named Eko) alone on a Roblox-like island for 30 hours with no task. They set their own goals, such as climbing the highest point or seeing how high a stone can be thrown; arranged stones into hearts, their own names and the Cassiopeia star map; and invented games like basketball and "the floor is lava". Once one caught a toss 50 times in a row, then judged it too easy to count and redid it under stricter rules. The key result: agents that had played for 30 hours did better on concrete tasks than fresh copies, and deleting content from their memory files lowered performance. The paper isn't peer-reviewed yet, and Berkeley scholars caution it may just be the model imitating people as prompted. [MIT Technology Review](https://www.technologyreview.com/2026/10/19/1147095/ai-stranded-claude-virtual-desert-island-play/)
> [zh] **把 Claude 一个人丢在虚拟荒岛上，它开始「玩」了**：MIT CSAIL 的研究者把多份 Claude Opus 4.7（起名 Eko）单独放在一个类似 Roblox 的岛上 30 小时，不给任何任务。它们自己定目标，比如爬最高点、看石块能扔多高；用石块拼出心形、自己的名字和仙后座星图；还发明了篮球和「地板是岩浆」这类游戏。有一次它连续接住 50 次抛物，又觉得太快不算数，改了更严的规则重来。关键结果是，玩过 30 小时的 agent 之后做具体任务比新开的副本强，删掉它们记忆文件里的内容，表现就会下降。论文还没经过同行评审，伯克利的学者提醒，也可能只是模型在按提示模仿人。
